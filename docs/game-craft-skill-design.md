# game-craft Skill 设计调研

> 状态：Proposed
> 日期：2026-10-21
> 范围：游戏模式设计判断技能的内容边界、参考文档拆分、路由与接入方式
> 不包含：技能正文实现、运行时提示词改造、配置资源新增、自管理网页游戏（`docs/game-developer-guide.md`）

## 1. 决策摘要

1. `game-craft` 是**设计期判断层**，与 `novel-craft` 平级。`configuration` 是机制层，Game Agent 运行时提示是执行层，三者不重复。
2. 游戏的最小完整构建是**资料库 + 索引**。状态、规则、事件、规划按“是否改变玩家决策”逐项增加，不默认全开。
3. 酒馆素材迁移的是**内容与表达意图**，不是激活机制。关键词激活、概率、递归、scan depth、sticky/cooldown、Prompt Manager 顺序和 token 预算截断都不进入 Denova 设计。
4. **酒馆角色卡不是游戏。** 导入得到角色、声音和场景；核心循环、选择、失败、状态和成长仍需重新设计。
5. 建议 `1 个 SKILL.md + 6 个参考文档`，按作者任务路由，单次只读 1–2 个。
6. frontmatter 建议 `category: game`、`agent: general,ide`。不加入 `interactive_story`：运行时已有完整回合协议和叙事原则，设计手册进入游戏期目录只会增加噪声。
7. 打包不需要后端注册：发布构建直接复制仓库 `skills/` 目录（`scripts/build.sh:62`）。新增分类需要前端两处小改。

## 2. 现状：Denova 已经提供了什么

| 层次 | 现有实现 | 作者是谁 |
| --- | --- | --- |
| 世界与人物事实 | Lore 条目、Lore Index（resident / auto / manual，name / brief / full） | 有 `write_lore_items` 的 Agent（IDE）或资料库界面 |
| 持久状态 | State System：Actor 模板、类型化字段、初始 Actor、trait pool | General / IDE + `config_read` / `config_apply` |
| 判定 | Rule System：d20 检定模板、难度、状态绑定、四种结果 | 同上 |
| 事件供给 | Event Package：事件卡、类型、强度、标签 | 同上 |
| 长期规划 | Game Planning 模板 + 故事级 `planning_mode` / `planning_template_id` | 同上 + 故事创建界面 |
| 模块组合 | 故事创建时的 `module_refs`：叙事风格、状态、规则、事件包、图像 | 故事创建界面 |
| 叙事风格 | `narrative_style`：`system` / `turn_context` 槽位、风格参考、场景映射 | General / IDE + 配置或界面 |
| 开场 | 故事创建时的 opening；酒馆首条消息导入为开场预设 | 故事创建界面 / 导入 |
| 每回合执行 | Game Agent 提示已包含回合协议、资料召回、检定、`state_changes`、`choices`、`plan_update` | 运行时 |

结论：**机制层已经完整，缺的是“该不该建、建成什么样、怎么判断好不好”的判断层。** 运行时提示已经把每个回合怎么写讲清楚了，`game-craft` 不应再写一遍。

三个 Agent 的工具边界值得写进技能：

- `interactive_story` 只有资料读取、Skills、回合工具，没有配置写入、资料写入和文件写入；游戏进行中不能改设定。
- `general` 有 `config_read` / `config_apply`，但没有 `write_lore_items`；能做模块配置，不能写资料正文。
- `ide` 同时有配置和资料写入；完整的游戏构建通常需要它，或由资料库界面补齐正文。

## 3. 酒馆经验映射

调研来源：Character Card V2 / V3 规范、SillyTavern World Info 与 Prompt Manager 文档。酒馆真正成熟的是**人格稳定性、资料检索和提示分层**；它不解决游戏循环、失败和成长。

| 酒馆概念 | 它实际解决什么 | Denova 落点 | 保留 | 丢弃或改写 |
| --- | --- | --- | --- | --- |
| 角色卡 description / personality | 人格与外观的稳定描述 | 角色 Lore 条目，常驻或 auto | 具体事实、关系、边界、说话方式 | 形容词堆砌；卡片里的全局规则移到叙事风格 |
| scenario | 初始场景 | 开场 + 当前场景 Lore | 地点、时刻、在场人物、即时压力 | 背景介绍式写法；改成可行动场景 |
| first_mes / alternate_greetings | 开场白 | 故事 opening 预设 | 语气、钩子、第一印象 | 自问自答或封闭结尾；开场必须留下行动空间 |
| example_dialogue | 声音校准 | 角色 Lore 的“说话示例” | 2–4 句典型对白 | 大段对话全集；只保留能区分声音的样本 |
| 卡片 system_prompt | 角色扮演约束 | `narrative_style` 的 `system` 槽位或内置叙事风格 | 视角、语气、禁忌 | 覆盖游戏规则或回合协议的内容 |
| post_history_instructions | 每回合提醒 | `narrative_style` 的 `turn_context` 槽位 | 持续强调的行为约束 | 重复注入大段设定；设定应进 Lore |
| 世界书条目 | 世界事实 | 独立 Lore 条目 | 正文；关键词作为检索线索 | 关键词自动激活、概率、递归、scan depth、sticky/cooldown |
| `constant` 条目 | 始终在场 | `load_mode=resident` 或自定义组 `full` | 常驻内容 | 大量条目设为 constant |
| insertion order / depth | 提示位置 | Denova 固定装配顺序；用 `system` / `turn_context` 表达稳定与每回合 | “稳定 vs 临时”的意图 | 具体 depth / order 数值 |
| token budget | 上下文成本 | Index detail（name / brief / full）+ resident 预算 | 分层思想 | 自动截断；Denova 超限明确报错 |
| MVU 变量 | 持久状态 | State System + `state_changes` | 会改变决策的量 | 正文里的变量块、隐藏公式 |
| 掷骰 / 脚本 | 判定 | Rule System d20 + state bindings | 失败推进、难度、代价 | 任意脚本与公式；只支持 d20 |

### 3.1 为什么角色卡不是游戏

| | 酒馆角色卡 | Denova 互动故事 |
| --- | --- | --- |
| 单位 | 一个角色或一个聊天场景 | 一个可持续运行的玩家处境 |
| 推进 | 开放对话，模型即兴回应 | 玩家行动 → 世界裁定 → 状态变化 → 新选择 |
| 失败 | 通常没有 | 必须有代价、分支或终止条件 |
| 记忆 | 依赖聊天历史和世界书 | Lore（稳定）+ State（当前）+ Turns（历史）+ Plan（未来） |
| 规则 | 模型自由裁定 | 可选但可执行的 d20 检定与状态绑定 |

导入一张卡只能得到“演员和布景”。**核心循环、玩家目标、选择代价、失败推进和成长线，必须在导入后重新设计。**

## 4. 一个游戏要构建什么

### 4.1 必建：资料库

最小资料库应覆盖：

- 世界底线 3–7 条：什么可能、什么不可能、代价是什么、有哪些禁忌。
- 主角：固定角色写成 Lore；可自定义的主角写成角色模板或初始 Actor。
- 当前场景：地点、时刻、在场人物、可交互物、即时压力。
- 活跃角色：当前会互动的 2–5 人，常驻或 `full`。
- 候场角色：可能登场的人，auto + brief 即可发现。
- 与循环直接相关的地点、势力、物品和规则。

### 4.2 可选模块：按“是否改变玩家决策”判断

| 模块 | 需要 | 不需要 | 最小实现 |
| --- | --- | --- | --- |
| State System | 资源、关系、伤势、时间压力跨回合变化，玩家会据此决策 | 一次性剧情；模型能稳定记住的事实 | 1 个主角模板 + 4–8 个字段 |
| Rule System | 结果不确定、失败有意义、玩家能通过准备改变胜率 | 叙事可以合理裁定；失败没有分支 | 1 套 d20 模板 + must/skip 示例 |
| Event Package | 需要外部压力、随机性、类型化桥段 | 线性主线已足够；事件会打断玩家目标 | 3–8 张事件卡 |
| Game Planning | 长篇、主线、伏笔、角色登场和分支需要管理 | 短篇、纯沙盒、完全即兴 | 选内置模板或写一个自定义模板 |
| Narrative Style | 需要稳定语气、视角或禁忌 | 内置叙事风格已够用 | 1–2 个槽位，不复制设定 |
| 图像预设 | 需要稳定角色/场景视觉 | 纯文字 | 可选 |

### 4.3 成熟度阶梯

- **L0 最小可玩**：定位 + 循环 + 主角 + 当前场景 + 3–5 个可交互对象 + 开场。不需要状态、规则、规划。
- **L1 可连载**：资料库分层 + Index 分组 + 核心资源状态 + 规划模板。
- **L2 有判定**：规则系统 + 状态绑定 + 失败分级。
- **L3 有导演**：事件包 + 规划维护 + 风格/提示分层 + 图像。

先让 L0 可玩，再按实际缺口加模块；不要为了“完整”一次开满。

## 5. `game-craft` 的定位与边界

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| `game-craft` 判断层 | 循环、选择、失败、资料分层、状态取舍、规则取舍、事件与节奏、开场、诊断 | 字段 schema、修订号、写入、运行时回合协议 |
| `configuration` 机制层 | `config_read` / `config_apply`、资源字段、完整替换语义、修订校验 | 该不该建、建成什么样 |
| Game Agent 运行时 | 每回合叙事、召回、检定调用、`state_changes` / `choices` / `plan_update` | 设计期配置与资料写入 |

技能正文应明确：

- 只给判断、模板和诊断，不决定执行流程；执行顺序由当前 Agent 和用户任务决定。
- 不复制 `configuration` 的字段表；需要具体值时读取对应参考文档。
- 不复制运行时回合规则；只说明“要写成什么样，运行时才能执行”。
- 资料正文用 `write_lore_items`；索引和模块用 `config_read` / `config_apply`；不直接改 `.denova` 或 JSON。
- 当前 Agent 没有资料写入能力时，把正文写入交给有能力的 Agent 或资料库界面，不绕过工具。
- 游戏进行中要改配置，交给 General / IDE Agent；Game Agent 只读。

skills/game-craft/

  references/

### 6.1 `SKILL.md`

frontmatter：

```yaml
---
name: game-craft
description: 互动叙事游戏设计判断手册。作者要求游戏定位、核心循环、资料库与世界书、状态与规则、事件与规划、开场与提示词、酒馆素材迁移或试玩诊断时使用；提供判断、模板与诊断，不负责配置写入、文件写入与运行时执行。
category: game
agent: general,ide
---
```

正文结构与 `novel-craft` 对齐：

1. **开工前先确认三件事**
   - 玩家反复做什么（循环）。
   - 哪些事实不能变（硬设定与语气边界）。
   - 这一回合玩家在期待什么（目标、风险、选择）。
2. **六条核心判断**

| 原则 | 操作问题 | 常见失效 |
| --- | --- | --- |
| 先定循环，再堆内容 | 玩家每回合重复做什么？什么在变？ | 只有世界观，没有可玩的重复动作 |
| 让选择有代价 | 每个选项放弃了什么？后果何时可见？ | 选项只是换措辞，结果相同 |
| 让失败继续故事 | 失败后玩家还能做什么？ | 失败 = 重来、卡死或作者硬救 |
| 按需分层加载资料 | 这条事实每回合都必须知道吗？ | 全塞常驻导致上下文爆炸；全放 auto 导致模型想不起来 |
| 只记录会改变决策的状态 | 这个数值改变玩家下一步吗？ | 为每个设定建字段，维护成本高且没人用 |
| 规则制造取舍 | 检定前玩家能做什么准备？失败有什么不同？ | 什么都掷骰，或掷骰不改变结果 |

3. **场景路由表**（见 6.2）。
4. **最小可玩结构**

```
玩家目标 → 可见信息 → 2–3 个有代价的行动 → 裁定（规则或叙事）
→ 世界回应 → 局势/关系/信息/资源变化 → 新的选择
```

- 开场必须完成一次完整循环。
- 每回合至少改变一项：局势、关系、信息、资源、位置、时间或风险。
- 失败也产生新选择。
5. **交付前检查**：循环可重复；选择有代价；失败可继续；资料分层合理；状态字段会改变决策；规则只用于真实不确定性；每回合有变化；名字与事实一致；上下文在预算内；只交付作者要的范围。
6. **不要**：不要把酒馆卡直接当游戏；不要迁移激活机制；不要把所有设定设为 resident；不要为每个设定建字段；不要什么都掷骰；不要让选项只换措辞；不要让失败等于重来；不要用旁白替玩家做决定；不要在技能里直接写配置。
7. **与配置和运行时配合**：三层职责、工具边界、进行中改配置的转交方式。

### 6.3 六个参考文档的内容要点

#### `premise-and-loop.md`

- 体验目标：探索、生存、关系、权谋、解谜、成长、经营、恐怖、喜剧；主体验 1 个，副体验最多 1 个。
- 规模：单局、短篇（3–10 回合）、中篇（一个 arc）、长篇；规模决定是否需要状态与规划。
- 一句话游戏模板：玩家是【谁】，在【世界】里反复【做什么】，为了【什么】，每次行动要面对【什么取舍】。
- 核心循环六问：玩家看到什么、能做什么、如何裁定、世界如何回应、什么被改变、下一个决定从哪来。
- 选择设计：2–4 个方向不同的选项；从收益、代价、风险、时间、关系、信息、道德中至少两个维度制造差异；避免支配选项、假选项和唯一正解。
- 失败设计：成功但有代价、部分成功、复杂化、带新信息的挫折、不可逆损失（少用）；避免重试循环、死路、作者硬救和随机惩罚。
- 开场：第一回合交代谁、在哪、此刻要什么、什么危险、第一个有意义的选择；不倾倒设定；酒馆首条消息只能作为原料，必须改写成可行动的开场。
- L0 最小可玩清单与检查。

#### `lore-and-worldbook.md`

- 记录位置分工：Lore 是稳定事实，State 是当前可变值，Plan 是未来意图，Turns 是已发生历史；同一事实只放一处。
- 游戏必建清单：世界底线、主角、当前场景、活跃角色、候场角色、循环涉及的地点/势力/物品/规则。
- 角色条目模板：身份、外观、性格、说话示例、想要/害怕/底线、关系、知道与不知道、可交互点、秘密、可变的候选字段。
- 地点/势力/物品/世界规则模板；写成可执行约束，不写成小说段落。
- 分层原则：resident 只放每回合必须知道的；auto 放“名字可发现、正文按需读”；manual 放隐藏、剧透和一次性内容。
- Index 分组按使用场景或 arc，不按百科分类；组名、purpose、body 说明“何时查阅”；default_detail 用 `brief`，只有核心组用 `full`。
- 预算：resident 32 KiB 只是警告线，不是目标；Index 默认 64 KiB、渲染上限 1088 KiB；超限明确报错，不静默截断。
- 酒馆迁移：映射表、逐字段改写、导入后去重/改名/补 brief/设分层/建组/查矛盾。
- 反模式：整本设定常驻；用关键词赌模型会想起；条目写成文学描写；同一事实在 Lore、State、Plan 各写一份。

#### `state-and-rules.md`

- 何时需要状态：跨回合、玩家在意、能据此行动、有可见后果的量。
- 何时不要：一次性事实、Lore 已固定的稳定事实、没人读取的数值、模型能稳定推断的内容。
- Actor 设计：主角、重要 NPC，必要时一个“世界/时钟”Actor 承载全局压力；不要给每个路人建 Actor。
- 字段设计：4–8 个字段为常见规模；`description` 说明含义，`update_instruction` 说明触发条件与“替换还是增量”；用 `group` 和 `display` 控制面板可读性。
- 初值与 trait pool：trait 用来给行为着色，不替代数值；一次模板最多 24 个 trait。
- 隐藏状态必须有可观察信号；玩家看不到的数值不能成为唯一反馈。
- 规则何时加：结果不确定 + 失败有意义 + 玩家能准备；普通观察、对话、短移动不检定。
- d20 规则设计：难度梯度、优势/劣势、状态修正；`must_check_examples` / `skip_check_examples` 写具体例子，这是模型的校准器。
- 失败策略：`fail_forward` / `success_at_cost` / `blocked` / `hard_failure`；关键路径慎用 `hard_failure`，除非它就是终止条件。
- 状态绑定：只保留少量可读公式；修正是玩家能理解的来源；结果变化由后端计算，正文不重复算。
- 可见性：`audit_only` 与 `public_roll` 的取舍；玩家应能推断大致胜率。
- 成长：新选项优先于更大数字；装备、关系、名声、情报都可以是成长。
- 最小规则集：无规则 → 单一检定 → 资源 + 时钟 → 完整 d20 + 绑定。

#### `direction-and-events.md`

- 四种事实分开：Lore（稳定 canon）、State（当前投影）、Turns（已发生历史）、Plan（未来意图且可修改）。
- 何时开启规划：长篇、主线、伏笔、角色登场、分支管理；短篇/沙盒可以关闭。
- 规划模板：解释内置默认模板的七个段落（长期方向、中期 arc、近期节拍、角色部署、线索与兑现、分支可能、连续性与重规划），以及 directed-longform 的段落；自定义模板必须是有序 H2 段落，写未来意图，不写已完成回合、精确状态和行动标签。
- 近期分支只写 2–4 个候选场景；远期方向保持简洁；写重规划触发条件。
- 事件卡：触发场景、背景融合、事件逻辑、后果与恢复、收益与代价、选择约束；事件是压力与机会，不是必须执行的剧本。
- 事件选择：与玩家目标交叉，而不是打断目标；控制频率与强度；同一桥段不要连续复用。
- 分支：在 meaningful decision 处分叉；允许汇合但不抹掉选择后果；用状态/关系/信息承载差异，避免指数级分支。
- 节奏：铺垫 → 升级 → 兑现 → 喘息；长期高压会钝化；用 downtime 积累关系与人物。
- 诊断：原地打转、强行拉回、事件刷屏、没有 stakes、主线漂移。

#### `voice-and-prompting.md`

- 提示分层：稳定身份/语气/禁忌 → `system`；每回合强调的行为约束 → `turn_context`；事实 → Lore；数字与当前状态 → State；未来意图 → Plan；事件压力 → Event Package。
- 作者注释（author's note）的迁移：保留“每回合都要强调”的内容，删掉大段设定复述；不要与 Lore 冲突。
- 角色卡 system_prompt 的迁移：只保留角色扮演约束；不能覆盖回合协议、检定规则和输出格式。
- 内置叙事风格与自定义风格的选择：先用内置，确有稳定差异再自定义。
- 风格参考：只用于语气、节奏、叙述方式，不复制人物、情节和设定；按场景映射，不全局硬套。
- 槽位写法：短、具体、可执行；一条槽位只负责一类约束；避免同义重复和互相矛盾。
- 游戏特有约束：不要把“必须给 3 个选项”“必须更新状态”写进风格槽位，运行时已经负责；风格只负责表达。
- 上下文预算：常驻槽位越短越好；长参考放 `style_reference` 按需读取。

#### `playtest-and-diagnosis.md`

症状表：

| 症状 | 可能原因 | 证据 | 最小修复 |
| --- | --- | --- | --- |
| 玩家不知道能做什么 | 开场缺目标/可交互物；选项空泛 | 首回合玩家提问或沉默 | 补一个具体目标 + 3 个可感知行动 |
| 选择没意义 | 选项汇合、无代价、存在支配解 | 连续两回合选不同项结果相同 | 重写选项的代价与后果；加状态变化 |
| 剧情原地打转 | 每回合没有变化；缺少压力 | 回合结束局势不变 | 加时钟/势力行动/事件；定义每回合变化项 |
| 模型忘记设定 | 核心资料没常驻；Index 缺 brief；名字不一致 | 同一角色前后矛盾 | 核心升 resident；补 brief；统一名字 |
| 上下文超限/变慢 | resident 过大；大量 full；Index 膨胀 | 预览或日志显示接近上限 | 降到 auto/brief；拆条目；删重复 |
| NPC 像工具人 | 没有目标、秘密和信息边界 | NPC 只回答、不行动 | 补想要/害怕/知道什么；给独立议程 |
| 检定太多/太少 | must/skip 示例缺失；触发条件过宽 | 普通对话也掷骰，或关键风险不掷 | 重写示例；限定为有风险/不可逆的行动 |
| 失败即卡死 | 关键路径用 hard_failure；没有 fail-forward | 失败后无选项 | 改失败策略；补复杂化或代价 |
| 重复桥段 | 事件包单一；规划没有新问题 | 同类事件连续出现 | 轮换事件；加阶段变化 |
| 主线被带偏或强行拉回 | 规划过刚或过松 | 玩家选择被无视 | 选 directed 模板；写重规划触发；留分支承接 |
| 语气不一致 | 风格槽位冲突；Lore 文风混杂 | 同一角色多种腔调 | 合并 system 槽位；统一条目写法 |
| 节奏拖沓/过快 | 每回合目标字数或场景密度不合适 | 大量无决策回合 | 调整目标字数；削减低风险回合 |

诊断方法：

1. 以玩家身份玩 3–5 回合，记录“我想做什么”和“游戏给了我什么”。
2. 检查模型实际看到的上下文：Lore Index、常驻资料、状态手册、规划、风格槽位。
3. 定位到层：循环、资料、状态、规则、方向、表达或运行时设置。
4. 一次只改一处，重放同一场景，比较差异。
5. 不要重写整个游戏；先找最小有效修复。

验收清单：新玩家一回合内能说出目标；至少两个选项在代价/风险/信息上不同；每回合至少改变一项；失败可继续；核心角色和硬规则不需要猜；状态只在正文确认后更新；上下文在预算内；语气跨回合一致。

## 7. 接入方式

### 7.1 技能发现

当前没有 `game-standard` / `game-lite` 之类的游戏流程技能会自动加载 `game-craft`。建议 v1 依赖 Skill 目录的 description 路由和显式 `/game-craft`：

- description 覆盖：游戏、互动故事、资料库、世界书、角色卡、状态、规则、检定、事件、规划、开场、酒馆、试玩。
- 目录描述上限 1024 字节，中文描述控制在 300 字以内。
- 若后续需要“从零建游戏”的端到端引导，再单独评估 `game-build` 流程技能；不要让 `game-craft` 自己承担流程编排。

### 7.2 Agent 范围

`agent: general,ide`：

- General 可做定位、循环、模块取舍、配置建议和诊断。
- IDE 可写资料正文，是完整构建的主力。
- `interactive_story` 不加载：它没有配置/资料写入能力，运行时提示已覆盖回合写作；把设计手册放进游戏期目录会增加上下文和误用风险。

### 7.3 分类

建议新增 `category: game`：

- `web/src/features/skills/skill-utils.ts`：`skillCategoryOptions` 增加 `'game'`。
- `web/src/i18n/locales/zh-CN/skills.ts`：`skills.category.game: '游戏'`。
- `web/src/i18n/locales/en-US/skills.ts`：`skills.category.game: 'Game'`。

未加入选项时前端会把未知分类原样显示为 `game`，功能可用但不本地化；建议一并补齐。

### 7.4 打包与验证

- 打包：`scripts/build.sh` 和 `scripts/build-github-release.sh` 都会复制 `skills/`，无需代码注册。
- 静态检查：`pnpm --dir web check:i18n`（若改分类文案）；技能内容用 markdown 检查。
- 行为验证：用三个场景 dry-run：
  1. 导入一张酒馆角色卡 + 世界书，改造成 5 回合可玩的短篇。
  2. 从零设计一个带状态和 d20 检定的中篇。
  3. 诊断一个“选择没意义、剧情原地打转”的现有游戏。
- 检查技能没有复制配置字段和运行时协议：grep `update_instruction`、`revision`、`submit_interactive_turn` 等，应只作为“交给对应层”的引用出现。
