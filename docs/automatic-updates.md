# 自动更新与故障恢复

Denova 保留便携目录与独立 `denova-updater`，不引入常驻更新服务。更新只替换发行包管理的程序、内置 Skills、工具与许可证；配置和 `.denova` 用户数据由应用管理，不在更新器的覆盖或回滚范围内。

正式构建直接提供二进制内嵌的前端，前后端始终来自同一构建，不解压到临时目录，也不读取安装目录或工作目录中的旧 `web/`。开发构建继续使用 Vite 或磁盘资源。发行包保留 v0.5.1 校验所需的空 `web/` 目录；新版 updater 不再替换独立前端目录。

## 后台检查与重启时机

正式构建在启动五秒后开始由后端检查更新，随后每 6 小时检查一次，不依赖页面是否打开。设置页的“自动检查更新”沿用原有默认开启值；新增“自动下载更新”默认关闭。两项设置均来自用户级 `.denova/config.toml`，不随当前 Project 改变。关闭自动检查也会停止后续自动下载；已经开始的下载可以完成。开发构建不运行自动检查。

后台下载复用相同的校验、续传和暂存流程，前端读取统一状态。已经暂存的包不会被定时检查覆盖。下载失败最多每小时再尝试一次；安装失败的同一版本只允许用户主动重试，发现新版后才恢复自动准备。后台检查、下载进度和错误是进程内状态，已暂存包和安装结果仍以持久事务为准。

暂存完成后可选择立即重启，或等待任务完成后重启。等待覆盖写作、游戏、通用对话、自动化、图片等已接纳的操作，以及仍运行的 Native 子 Agent；不限制任务运行时长。等待可以取消，普通进程退出会取消等待意图。真正重启前在任务接纳锁内再次确认空闲并阻止新操作，updater 接管失败时恢复接纳。等待绑定同一个更新事务，安装包发生变化不会悄悄改为安装另一版本。

## 下载与发布

- 一次安装只读取一次 GitHub Release，压缩包与 `checksums.txt` 来自同一份元数据。
- 下载按 SHA-256 分目录保存，使用已有 grab 库续传并校验完整文件。网络中断和可重试服务端错误最多重试三次；重试耗尽保留可续传的部分文件。损坏内容不会进入安装阶段。
- 网络请求使用显式代理环境变量或已存在的系统代理探测能力；状态查询不触发外部请求。
- Release 工作流先创建草稿，完整上传全部平台产物和校验和后才公开。已公开的同版本产物不能覆盖；修正需要发布新版本。
- SHA-256 检测下载损坏与资源错配，信任来源仍是 GitHub Release 与 HTTPS。目前没有独立的发行包签名密钥体系。

## 安装事务

`.denova-updates/pending-manifest.json` 以相对路径指向当前事务；事务目录保存 `manifest.json`、暂存发行包、`backup/` 和 `apply.log`。清单保存事务状态、可执行文件名与启动参数；安装、暂存、备份和日志路径按清单所在位置推导，移动整个便携目录后仍可读取和恢复事务。用户明确传入的外部路径参数保持原义。记录先写临时文件并同步，再替换原记录。进程内互斥与安装目录文件锁共同防止重复安装。Windows 上仅对短暂的共享/访问锁重试文件替换，最多一秒；不删除原文件来绕过锁。

| 状态 | 行为与恢复边界 |
| --- | --- |
| `staged` | 安装包已校验、解压并准备好，程序尚未修改；设置页重开后可继续安装。 |
| `waiting` | updater 已接手，持续等待原进程退出，不因关闭耗时超过固定期限而放弃重启。HTTP 返回后，应用先调用 `App.Close` 清理任务与资源，再退出。 |
| `backing_up` | 完整复制当前发行文件；此阶段不修改原文件。 |
| `applying` | 完整备份及原文件列表已落盘，开始替换。先放置带启动保护的新主程序；单个文件经同步的临时文件替换，目录逐项更新。 |
| `starting` | 新程序已经发起启动。它必须初始化应用、开始提供 HTTP 服务，并核对更新 ID 和目标版本后写入就绪凭据。 |
| `rolling_back` | 从完整备份恢复，最后恢复主程序；备份保留，因此恢复可重复执行。 |
| `succeeded` | updater 收到匹配的就绪凭据并记录成功，前端才刷新。保留本次备份与日志，清理旧暂存包和下载缓存。 |
| `failed` | 错误保存在事务与日志中。设置页展示失败和相对于安装目录的日志路径，允许重新准备安装包。 |

程序在读取配置或打开用户数据之前检查事务。替换或恢复被中断时，下一次启动把工作交回暂存 updater；恢复完整旧文件后才重新打开应用。等待或备份阶段的中断保留原程序。启动确认已经写入、但 updater 尚未来得及记录成功的事务，下次启动可以完成成功记录。

新进程在原后端端口启动。前端同时核对更新 ID、成功状态和运行版本，避免旧进程仍能响应时提前刷新；断网、启动失败与等待超时都会结束等待或提供可操作的错误提示。

helper 接管失败时，原程序先终止并回收未确认的 helper，再将事务恢复为可重试的 `staged`，无需重新下载。下载、上传或应用请求失败后，设置页重新读取持久状态；即使响应丢失，也能恢复已暂存的包或继续等待已经开始的更新。

## 故障处理边界

- 替换失败、或操作系统未能启动新进程：恢复完整旧程序文件并尝试启动旧版。
- 新进程已经开始运行，却未在 90 秒内确认就绪：保留新程序和旧程序备份并记录失败。新程序可能已经迁移用户数据，因此不能自动降级二进制。检查 `apply.log` 与应用日志，必要时重新安装发行包；不要只还原旧可执行文件来绕过数据兼容检查。
- 前端最长等待三分钟；页面关闭会取消轮询，但不会中止后台安装。重新打开设置可读取持久状态。
- 文件被其他程序占用、磁盘空间不足或写权限不足可能阻止替换或恢复。错误会保留；处理原因后重新启动可继续中断的恢复。备份也写不完整时，原程序文件仍保持完整。
- 这套确认覆盖程序初始化与 HTTP 服务就绪，不替代所有业务功能的发布回归，也不承诺对任意硬件损坏进行恢复。

v0.5.1 的旧暂存清单会在 updater 接手时补齐事务 ID、状态和来源版本，并转换为上述记录格式；其尚未使用的旧备份路径不参与新事务。无需用户数据迁移。v0.5.1 已在运行的旧前端和退出流程，要到下一次启动新版后才具有新的状态展示与清理行为。

v0.5.1 没有记录实际监听端口，且更新重启会禁止再打开浏览器。updater 因此通过进程级 `DENOVA_UPDATE_FROM_VERSION` 传递本次更新的来源版本；新版在具有更新 ID 的 v0.5.1 交接启动中沿用旧默认端口 `8080`，避免旧页面继续请求 `8080`、新服务却已切到 `7789`。该值只作用于默认配置层，启动配置、用户配置、端口环境变量和显式 `--port` 参数仍然优先，不改写用户设置。后续更新会替换来源版本，回滚不携带该提示；普通手动启动仍使用当前默认端口 `7789` 并打开对应页面。Windows 使用系统 URL 关联打开浏览器，不依赖 PATH 中的 `cmd`。

## 验证

```powershell
go test ./internal/update
go test -tags integration ./internal/update
go vet ./internal/update
pnpm --dir web test:unit -- src/features/settings/UpdateSettings.test.tsx src/features/settings/update-reload.test.ts
pnpm --dir web test:browser manual-update.spec.ts
```

带 `integration` 标签的测试编译真实进程夹具与 updater，在临时安装目录内验证进程交接、退出清理、文件替换、HTTP 就绪确认和中断后的启动恢复，并覆盖移动整个目录后的暂存、成功和中断事务，以及 v0.5.1 无端口参数升级后仍在旧浏览器地址提供服务。默认端口回归用例在 `8080` 已被占用时跳过，其他用例使用系统分配的隔离端口。慢关闭通过 Go 虚拟时钟验证超过原 60 秒期限的等待，无需延长实际测试时间。CI 在 Windows、macOS、Linux 原生运行这些测试；交叉编译不能替代它们。
